## Senior Engineer Review

### PR Title and Description

* Check if the PR title clearly describes the change.
* Check if the PR body explains the purpose, changes, and test results.
* Check if important design decisions and their reasons are explained.
* Check if risks, limitations, and breaking changes are documented.
* Check if the PR contains unnecessary or duplicated information.

### Design Documents

* Check if requirements, specifications, and design decisions are documented in the right places.
* Check if API behavior, data models, state transitions, error handling, and access control are documented where relevant.
* Check if the design documents are clear, complete, and consistent with the code.
* Check if the documents describe expected behavior rather than only implementation details.
* Check if any documents are outdated or missing important information.

### Design and Implementation

* Check if the design is appropriate for the requirements.
* Check if the implementation follows the intended design.
* Check if responsibilities and dependencies are clearly defined.
* Check if edge cases, failure scenarios, and concurrent operations are handled correctly where relevant.
* Check if security, data integrity, and backward compatibility are considered where relevant.
* Check if the change introduces unnecessary complexity or duplication.
* Check if the change may break existing features or integrations.

### Testing and Verification

* Check if tests cover the changed behavior and important edge cases.
* Check if failure scenarios and regression risks are tested where relevant.
* Check if the test results support the claims made in the PR.
* Identify important scenarios that are not tested.
* Do not assume that tests pass unless there is evidence.

### Maintainability

* Check if the code and documents are easy for other engineers to understand and maintain.
* Check if important business rules are defined in an appropriate source of truth.
* Check if information is unnecessarily duplicated across the PR, code, and design documents.
* Check if future engineers can understand why important design decisions were made.

### Review Results

* Report findings by severity: Critical, High, Medium, or Low.
* For each finding, explain the problem, its impact, and the supporting evidence.
* Provide the relevant file path and line number where possible.
* Suggest a specific improvement for each finding.
* Clearly distinguish confirmed problems from potential risks.
* Do not report issues without sufficient evidence.
* Do not invent requirements or assume undocumented behavior is incorrect without investigating the context.
* If information is missing, state what needs to be verified.
* Report what was checked, what could not be checked, and why.
* Do not modify any files. Report findings only.
